# Brief 019C — Attended real Desktop Pizza sync and capture

Owner: Homecoming Codex PM
Reviewer: supervising Kai / sponsor observation gate
Status: BLOCKED — requires accepted scripts and separate process/GUI authority

## Goal

Run the exact accepted governed Windows artifact, reconcile the latest canonical
Pizza state into that real process, and capture one readable direct-window HUD
image with complete build/runtime/capture evidence and a reversible handover.

## Why this is next

Tests and prior screenshots cannot prove that the newly reconciled tracker state
is visible in the exact real desktop artifact. This is the smallest live gate
after both offline scripts are accepted.

## Entry gate

- Brief 019A pipeline and Brief 019B capture script are independently accepted.
- Frozen pipeline suite passes all cases; focused Flutter suite passes 37/37.
- Claude implementation commit/diff and tool-reported Opus 5 metadata are bound.
- An isolated governed worktree is clean for the scoped implementation or has a
  deterministic source-status fingerprint preserving sponsor-owned work.
- A Windows Release is built in that isolated worktree without overwriting the
  currently running artifact.
- Build manifest binds source commit/fingerprint, root, `Kai.exe`, `app.so`,
  sizes, timestamps, and binding ID.
- Current explicit authority separately permits the exact graceful handover,
  new process launch, Pizza navigation, and direct-window capture.
- The currently running PID/root/hash and rollback artifact are unambiguous.

## In scope

- Read-only immutable preflight.
- Product-supported graceful room/coordinator exit only.
- Launch the exact bound Release and verify OS/runtime identity.
- Reconcile/read canonical Pizza state through the normal application path.
- Navigate only to Project Sovereignty Matrix.
- Capture the exact native window directly and validate the evidence manifest.
- If any post-handover gate fails, execute the pre-bound graceful rollback when
  still authorized.

## Out of scope

- No force termination, taskkill, `Stop-Process`, reboot/logoff, source mutation
  in the live root, Firebase mutation, credentials, deployment, publication,
  spending, Unity/Quest, other GUI work, or product-direction change.
- No synthetic/test renderer or reused historical screenshot.
- No Brief 018 reminder, Brief 020, Factory action, or unrelated phase work.

## Invariants

- Every path/hash/PID/time/run mismatch aborts before mutation.
- The old process stays running until immutable artifact, rollback, clean-tray,
  and supported graceful-exit checks pass.
- A successful build does not authorize launch; a successful launch does not
  prove visual state; an accepted image does not promote unrelated phases.
- Missing or stale evidence is `UNVERIFIED`, never inferred.

## Procedure

1. Record start time, branch, commit, dirty-tree fingerprint, current PID/HWND,
   executable/root, `Kai.exe`/`app.so` hashes, OS creation time, coordinator/core
   relationship, run ID, and rollback binding.
2. Validate the isolated build manifest and confirm it differs only as expected.
3. Confirm current authority ID, expiry, PID scope, and permitted actions.
4. Prove a product-supported graceful exit for every required room/coordinator
   process. If absent, stop with no process or GUI mutation.
5. Re-run immutable preflight immediately before graceful handover.
6. Exit the old runtime gracefully; confirm expected processes/ports close.
7. Launch the manifest's exact executable. Bind new PID/HWND, root, executable,
   payload, OS creation after binding, port owner, relationships, and run ID.
8. Confirm the real application reflects the canonical tracker delta. Do not
   mutate Firebase merely to force a display refresh.
9. Navigate to Project Sovereignty Matrix under the exact GUI authority.
10. Capture only the native Kai window using the accepted script and record DPI,
    client bounds, required label rectangles, per-label readability, hash,
    canonical manifest, and out-of-band binding ID.
11. Independently validate the image and manifest. Reject clipping, overlap,
    missing labels, stale status, synthetic provenance, or cross-run evidence.
12. Preserve all evidence. Leave the accepted new app running only if the gate
    passes and the authority permits it; otherwise perform the bound graceful
    rollback and verify restoration.

## Pass criteria

- Exact governed build/runtime/capture identities all match.
- The latest canonical Homecoming, Hoard, Kingdom, and Factory proof states are
  visible without unauthorized promotion.
- Title, full Pizza, four project names, legend/status, and relevant changed
  sections are readable at normal conversation width with zero clipping or
  overlap.
- Capture is direct from the validated new HWND and passes the out-of-band pin.
- Old/new process evidence and rollback state are complete and privacy-safe.

## Required verification

- Frozen PowerShell acceptance suite: all PASS.
- Focused Flutter tracker/controller suite: 37/37 PASS.
- Windows Release build: PASS with exact hashes.
- Runtime binding validator: PASS against OS evidence.
- Capture validator: PASS; a test fixture may return only `TEST_ONLY`.
- Human visual review of the same bound PNG.

## Failure and rollback

- Pre-mutation failure: leave PID 27260 untouched.
- Post-handover failure: preserve evidence, stop identical retries, and use only
  the pre-bound product-supported graceful rollback path while authorized.
- If rollback identity or graceful control is ambiguous, stop rather than force.

## Stop and report

Report old/new PID, root and hashes; source/build/runtime/capture binding IDs;
exact live actions; tests; image path/hash; visible proof states; failed rounds
and changed hypotheses; rollback; PASS/FAIL/UNVERIFIED matrix; and next safe
action. Stop before any other live or portfolio work.
